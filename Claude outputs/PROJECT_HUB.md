## 🔒 PROJECT-WIDE OPERATING RULES (per Abram 8/27 — apply to EVERY task in this project, not just engine edits)
The FEATURE PROTECTION PROTOCOL below was written for the engine. Abram has extended its spirit to the whole project: **every limb on the tree is protected — engine, Mac agents, installers, vessel data, client docs, photo pipeline, publishing, and this hub.** These rules bind every chat, every workstream, every task.
1. **Read before you touch.** Start every task by reading this hub. Before changing any artifact, find its section here and read the KEEP bullets, the HOW THINGS ARE SAVED entry, and the gotchas that apply.
2. **Preserve everything that works.** A change that removes, weakens, or bypasses an existing behavior — a feature, an automation, a guard, a naming convention, a file location — is a defect unless Abram explicitly retired it. "I didn't know it was there" is exactly what this hub exists to prevent.
3. **Flag before you clip.** If a requested change *could* alter or break existing functionality anywhere (not only inside protected code), stop and tell Abram: name the thing at risk, say what would change and why, and get his OK before shipping. This is rule 4 of the engine protocol applied to all workstreams.
4. **Report every change to the hub, same chat, same day.** Any task that changes infrastructure, data flow, a file's location or name, an automation, a setting on the Mac, or a process must merge a note into the relevant hub section (never rewrite the hub — re-read it first, merge, keep every KEEP bullet). Mention the chat title and date so the tentacle can be traced.
5. **Snapshot the hub to the Hub Archive** after every hub edit (protocol rule 6 / HUB ARCHIVE section). No exceptions for "small" edits.
6. **Verify, then say what you verified.** A delivery states what was tested and how (diff, headless run, log line, screenshot), and states plainly what was NOT verified. Never describe something as installed, deployed, or working unless it was seen working (see the 8/27 router lesson).
7. **Least access.** Ask for the narrowest folder, permission, or scope that does the job. Never ask for a parent folder when a subfolder will do. Never touch anything outside the granted scope.
8. **Engine edits additionally follow EDIT_LOCK and the full FEATURE PROTECTION PROTOCOL below.**
9. **BILLED IS SEALED (added 9/17 per Abram).** A locked billing event is closed history. No feature, migration, recompute, rate change, rename or "improvement" may alter a billed line — in the engine, in the client doc, or in a vessel JSON. The engine enforces this in code (see the KEEP bullet); every chat must also respect it in judgment: if a change would touch billed content, it is wrong by default, and reopening happens only through the gated, logged unlock. **(9/22b: this now covers a billed entry's PHOTOS as well as its figures.)**
These rules are also the project's custom instructions (Project settings → Instructions) so a new chat is bound before it reads anything.

1. **Triple-lock every shipped feature:** when a feature ships, the shipping chat must add (a) a `KEEP IN EVERY BUILD` bullet in this hub's engine section naming a greppable marker (function name, element id, hex color), (b) a `KEEP IN EVERY BUILD` comment block in the engine source at the feature, and (c) a sentence in the hub's build-prompt note. A feature not noted here is not protected — noting it is part of shipping, not optional.
2. **Pre-flight check before shipping ANY build:** walk every `KEEP IN EVERY BUILD` bullet in this hub and grep the base file for its marker. Any missing marker = stale lineage: STOP, diff against the project doc `index.html`, port the missing feature forward, and only then ship. Never ship a build that silently drops a KEEP bullet. **A marker only protects what it actually names — see the 9/22 `importWorklistRequest` false alarm in History.**
3. **Hub edits are MERGES, never rewrites:** re-read this hub immediately before writing it, add into the freshest copy, and never delete or weaken a KEEP bullet. Only Abram can retire a protected feature; when he does, keep the bullet with "(RETIRED <date> per Abram)" so a later chat doesn't 'helpfully' restore it.
4. **Ask before changing the inside of protected code (added 8/24 per Abram; TIMING amended 9/30 — the ask goes BEFORE the code is written, not after it is built and delivered; Abram caught the 30a video build asking after the fact — "and if I didn't catch that then there is poo in the pool?"):** any edit that modifies the internals of a protected function or `KEEP` block — even in service of a feature Abram requested — must be flagged to Abram BEFORE the build ships: name the protected feature, say exactly what changes inside it and why, and get his OK. Working near protected code without altering it needs no ask; altering its internals always does. This is on top of the style contract's rule that ANY visible change beyond the ask is run past Abram first, protected or not.
5. `claude/EDIT_LOCK.md` governs WHO may edit the engine doc at a given moment; this protocol governs WHAT every edit must preserve.
5b. **RUN THE REGRESSION SUITE — `claude/tests/` (added 9/28 per Abram).** `node engine-regression.js <build.html> [--baseline <previous>]`, 35 behavioural checks plus the marker grep and a client-doc comparison. **Rule 2's grep catches a feature being DELETED; it cannot catch a feature being WRONG, or a path that was never wired at all.** Both have reached Abram: 24q shipped a Move that destroyed photos with **100% of the markers intact**, and 28b refused the drag gesture he actually uses while the ⠿-handle drag it did support passed every test written. The suite's README carries the harness traps already paid for (style strings re-serialise, the ⠿ handle is a leaf, stale Undo toasts, the picker opens from `fieldBtn`, `addPhotosToProject` is async, and WebKit cannot be installed in the sandbox) — read it before writing a new check, not after.
6. **Every hub edit produces an archive snapshot (added 8/27 per Abram — see HUB ARCHIVE below):** after writing this hub, the same chat files a dated copy plus a CHANGELOG entry into the OneDrive `Hub Archive` folder (or hands Abram the snapshot files if the folder isn't connected). 7. **A build made outside this project still gets a hub write-up (added 8/27 — 27g lesson):** when a build is authored in another project/chat and relayed into this one, the relaying chat owns the KEEP bullet, build-prompt sentence, and Current-state line. 27g shipped 8/27 with an EDIT_LOCK note only; its features were unprotected until this write-up.

## HOW THINGS ARE SAVED (added 8/27, chat "OPS: Safari JSON save → vessel router")
The one place to look when "saving isn't working." Each tentacle, end to end.

**A. Vessel data (JSON) — engine → vessel folder**
1. Engine Data menu → **⬇ Save Data** (`exportData(false)`) or **💾 Save Data As…** (`exportData(true)`).
2. Browser behavior:
   - **Safari (Abram's daily driver):** no save-picker API exists, so both buttons do a plain download named `TPM_<Vessel>_v<N>_<date>.json` (`_tpmExportName()`). It lands wherever Safari → Settings → General → "File download location" points — currently OneDrive **DOWNLOADS**.
   - **Chrome/Edge/Arc/Brave:** native Save dialog (`showSaveFilePicker`), and repeat Save Data re-writes the same file in place via `_tpmFileHandle`.
3. Safari's per-site download permission: the engine is opened as a local file, so the prompt reads *Do you want to allow downloads on ""?* (empty quotes = no domain). Fixed permanently 8/27: Safari → Settings → Websites → Downloads → "When visiting other websites" = **Allow**. If this is ever "Ask" again, click Allow — Cancel silently drops the save.
4. **Vessel JSON router** (LaunchAgent `com.turnpointmarine.vesselrouter`, installed 8/27 — see Mac automations) watches OneDrive DOWNLOADS. Any `.json` containing `_meta.vessel` is: slugified (`Sandi Louise` → `sandi-louise`), copied to `TPM/<slug>/current.json`, archived as `TPM/backupjsons/<slug>_<date>_<time>.json`, then REMOVED from DOWNLOADS, with a "TPM Router" macOS notification. Client name is not used — vessel name only; **the download's filename never matters.** Unknown vessel → folder created + notification. Non-engine JSONs are left alone. **Two guards (v2, 8/27):** files older than 10 min are ignored (logged once as `STALE`), and an incoming export whose `_meta.exportedAt` is older than the vessel's existing `current.json` is parked in `backupjsons/<slug>_OLDER-THAN-CURRENT_…` without touching `current.json`.
5. Manual fallback (what Abram did through 8/26): drag the download into the vessel folder and rename it `current.json`.
6. **Sealing note (added 9/17):** opening a vessel seals its billed entries in memory (BILLED IS SEALED lazy backfill) and toasts "Save Data to keep it" — the seal only reaches `current.json` on the next Save Data, so every vessel needs one pass of open → Save Data. **(9/22: the POSTED-ONLY TRAVEL SPLIT also re-derives unlocked travel figures on that same save.)**
- **FIXED in build 2026-08-27e (8/27):** the Safari fallback in `exportData` used to revoke the blob URL in the same tick as `a.click()`; Safari resolves downloads asynchronously so the URL was often dead → download arrived nameless ("Unknown", no `.json`, router never saw it), as "Zero KB — stopped", or not at all. **1. iPhone Shortcut "TPM Engine Photos"** — Share Sheet → Format Current Date → Choose from menu (vessel slug) → `Repeat with each item in Shortcut Input`:
  - `Convert Repeat Item to JPEG` → *Converted Image*
  - `Resize Converted Image to 480 × Auto Height` → *Resized Image*
  - `Encode Resized Image with base64` (Line Breaks: None) → thumbnail string
  - `Encode Converted Image with base64` (Line Breaks: None) → full string
  - `Get contents of URL` → POST JSON to the flow: `id, project (INBOX), vessel, filename, mime, fullB64, thumbB64`

**2. Power Automate flow "TPM Photo Upload"** (HTTP trigger `manual`) — `BlobName` compose → **`Create block blob (V2) 1`** writes `concat(outputs('BlobName'),'-thumb.jpg')` ← **this is the THUMBNAIL, despite the "1" suffix** → **`Create block blob (V2)`** writes `concat(outputs('BlobName'),'.jpg')` ← the FULL image → `FullUrl` / `ThumbUrl` composes → `Create blob (V2)` writes the `_pending/` marker → `Response` returns `{fullUrl, thumbUrl}`.
**Identify the two blob actions by their `name` parameter in Code view, NEVER by the title (added 9/22):** the titles differ only by a trailing `1` whose meaning is the opposite of what it looks like. `name` ending `-thumb.jpg` = the thumbnail action; plain `.jpg` = the full-image action. A 9/22 fix went into the wrong one and reproduced the identical error.
**Connection:** both blob actions run on `shared_azureblob-3` and it works (confirmed 9/22). The older note naming `shared_azureblob-1` as "the working connection" is STALE — but the underlying warning still holds: editing a blob action is exactly when a wrong connection likes to re-attach itself, so check the `connection` line in Code view after any edit.

**3. Engine tray** — Refresh (`fetchPendingPhotos`) lists `_pending/` via the Azure Blob List REST API (`?restype=container&comp=list&prefix=_pending/`), reads each marker, and takes in only markers whose `vessel` field slug-matches this engine's vessel (falling back to the blob-name prefix `_pending/<slug>-…`).

Storage: account `tpmphotos`, container `tpm-photos`. Needs **anonymous LIST** for the listing and **anonymous blob read** for the images — blob-level read alone is not enough for the list call. Blobs are written `application/octet-stream` by Power Automate; the engine handles this by fetching the bytes and re-wrapping them as `image/jpeg`, so don't "fix" it by trusting the stored content-type.

- **FIXED 9/22 (flow) — the thumb action now uses a LENGTH guard.** Full write-up: `claude/docs/photo-thumb-binding-2026-09-22.md`. - **DRAG AUTO-SCROLL (KEEP IN EVERY BUILD, added 9/24, shipped in build 2026-09-24d per Abram, Cowork chat "Sandi Louise time entries"):** Abram — *"when dragging and dropping a photo to a new project the screen won't scroll up or down. Can you make that happen with proper modulation?"* Photo moves between projects work by dragging a tile onto a project header (PHOTO MOVE BETWEEN PROJECTS), but the browser gives a drag NO native page scroll, so any target that was off-screen when the drag began was simply unreachable — on a vessel with a dozen projects that is most of them. A single `document`-level **capture** `dragover` listener records `{_dsX,_dsY}` and `_dsSeen`, then starts a `requestAnimationFrame` loop (`_dsTick`). **The loop scrolls off the LAST KNOWN pointer position, not off the event** — this is the whole design: scrolling from inside the event handler means the page creeps only while the mouse is jiggling and stops dead the instant you hold still at the edge, which is the exact moment you want it to keep going. `dragend` and `drop` stop it (`_dsStop`), plus a **2 s no-`dragover` deadman** inside the tick for a drag that ends without either — Safari has been known to do that. The listener is in CAPTURE phase so no downstream `stopPropagation` can blind it. `_dsScrollerAt(x,y)` walks up from `elementFromPoint` for the nearest ancestor with `overflowY` auto/scroll AND real scroll range, so the field-capture tray or any inner scroller auto-scrolls too, and falls back to `window`; the band is measured against that scroller's own rect, not the viewport. **MODULATION — and the part worth remembering:** inside a 96px band, `t = (BAND − distance) / BAND` and px/frame = `DS_MIN + (DS_MAX − DS_MIN) · t²` (`DS_MIN` 0.8, `DS_MAX` 26). The first cut used a **cubic curve with no floor and the outer half of the band was a DEAD ZONE** — 0.04 px/frame rounds to nothing, so the band behaved as if it started 40px from the edge, which is not "proper modulation". Quadratic-from-a-floor gives a creep you can see the moment you enter the band. Sub-pixel steps accumulate in `_dsAcc` and are applied as WHOLE pixels, because a fractional `scrollTop` delta can be dropped outright — without the accumulator the slow end of the curve scrolls zero forever, which is how the dead zone was found. Frame-rate independent: the step is scaled by real elapsed time against a 16.7 ms baseline, capped at 64 ms so a stalled tab cannot lurch. Markers: `DRAG AUTO-SCROLL` / `_dsTick` / `_dsScrollerAt` / `_dsAcc`. **Purely additive — it touches no protected drag code** (the ⠿ handle, `photoDragSrcId`, the `photoId`/`fromPhotoProjId` tags and the project-header drop handler are all untouched), so no rule-4 ask was needed. ## History / gotchas learned the hard way
- **Never hand-write data a FEATURE is supposed to derive (9/24).** Abram: *"when I changed the labor hours on the line item from .75 to 1.25 the travel does not update"* and *"when labor entries are graduated to a billing event the travel needs to follow automatically"*. **Both features work** — proven headlessly on a clean card: changing 0.75→1.25 moved the derived share 0.38→0.52 and rewrote its description to "1.25 of 3 labor hrs", and graduating a labour entry graduated its travel onto the same billing event while leaving the other project's travel alone. **The cause was the data, and it was this chat's doing.** Sandi Louise holds **0 `travelDays` records and 59 cat-'V' entries, none carrying a `travelDayId`** — every travel line on that vessel is STATIC TEXT typed into the JSON during the September time-entry loading, written in the engine's own voice (*"prorated across the 2 projects worked that day by labor hours"*) so it reads exactly like a derived row. It is not one. `syncTravelDays()` finds no travel days and returns immediately, so nothing re-prorates and nothing follows graduation. Entry 1061 — the 0.37 Abram screenshotted — is one of them. **The rule: if a feature owns a calculation, load the data THROUGH that feature.** Hand-written output of a derivation is dead on arrival and, worse, looks alive — it cost two bug reports and a long diagnosis before anyone thought to check whether the rows were real. **The fix Abram chose is a full re-derive**, and the timing is lucky: all 59 are unbilled and none graduated, so nothing is sealed or on a locked invoice. Reconstruct one travel day per date (each date's shares sum EXACTLY to the day total its own description states — verified across all 19 dates, 21.75 hrs and $2,066.25), drop the static lines, let the engine derive. **Blocked on Abram's current export.**
- **Check whether the work is already in before you load it (9/24).** Abram asked twice, in good faith, to "load these time entries into the json" — and both tables were of entries already posted in the file, one of them the *breakdown document that had been generated from the file*. Loading either would have double- or triple-billed Hal, silently, because nothing in the engine refuses a duplicate. The tell was sitting on screen the whole time: In Flight read $17,393.42, which only reconciles if all of it is already posted. **When a batch is handed over for loading, total what is already in the file for that date range FIRST and say the number back.** And when a report is generated from the data, say so in its own header — the "Built from current.json … nothing written back" line is what made the check quick.
- **A style-string selector is not a test hook (9/24b).** The first headless probe for the ENGINE LIGHTBOX looked for `div[style*="z-index:4000"]` and reported the overlay had not opened — it had; the browser re-serializes `cssText`, so the attribute read back as `z-index: 4000` with a space. The overlay got `id="engineLightbox"` and `data-tpm-lightbox` and the test passed unchanged. Third time this project has paid for testing a rendered string instead of a stable attribute (see 22b's chevron and 9/24a's wrapper-matching probe): **give anything you will assert on an explicit hook at the moment you build it.**
- **The engine kept borrowing the client doc's affordances (9/24b).** Photos had a lightbox in the exported document from 8/13 and none in the engine for six weeks, because every photo feature was specified in terms of what the CLIENT would see. Abram works in the engine all day. When a feature is described by its client-facing half, ask what the engine-side half of it is before calling it done.
- **Arm a drag before the click, not during it (9/23e).** The photo handle set `draggable=true` on its tile inside `mousedown`. Chromium honors that; Safari decides whether a drag can start before that handler's change takes effect, so on Abram's Mac the photo simply never lifted — and every headless test passed, because the tests run Chromium. Make the thing you grab permanently draggable instead. Corollary: when Abram says "it doesn't work" and the Chromium test says it does, suspect the browser before suspecting him.
- **Don't offer a mapping that doesn't exist (9/24).** Asked whether a T&M project's Notes should move to Scope of Work "engine + client doc", the honest answer needed a look first: the client doc has no Scope of Work section at all, and notes already render as a subtitle under each project name in four places. Offering "engine + client doc" as a clean pair implied a symmetry that wasn't there. Reading the render sites before asking turned a vague yes into a narrow, provable change — engine only, with the doc byte-identical as the proof.
- **A test that can't tell two cards apart isn't a test (9/24).** The first headless probe for NOTES IN SCOPE FOR T&M matched a wrapper element for every project, so all three cards reported identical results and the assertion "passed" while proving nothing. The fix was to anchor on `.proj-body` and walk its direct children by index. **When every case returns the same answer, distrust the probe before the code** — the 9/22b "test the attribute, not the glyph" lesson in another costume.
- **Sending the file is not saving it (9/22–23).** Builds 22b and 23a were each verified, written up, and recorded in EDIT_LOCK as "saved" — and neither reached the project's `index.html`. The shipping chat had delivered the file into its conversation and treated that as shipping. Two builds sat in a chat for a day while the source of record said 22a; the next chat to build would have erased both. It was caught only because the next chat followed protocol rule 2 (re-pull after claiming the lock and check the stamp) instead of trusting the lock note. **A save is proven by reading it back:** after writing `index.html`, read it from the project and confirm the stamp (ideally `cmp` against the verified file) BEFORE writing UNLOCKED or a "last completed edit" note. The RELEASE CHECK block in `EDIT_LOCK.md` now says so where every engine chat reads it.
- **Put detail where its shape lives, and fold it elsewhere (9/23).** Travel is one drive split across a day's work, so per-entry travel rows in a project card were noise that also made the card hard to read as the story of a repair. Hiding them outright would have left a card whose visible rows no longer summed to its own subtotal. The fold keeps the money on screen in one line, points at the view where the detail makes sense, and still prints in full — and the proof it changed nothing but presentation was the same as 17d's: strip the fold markup and the document is character-identical to the previous build's.
- **An empty state is a design smell, not a feature (9/24).** The entry-photo picker had a carefully-worded panel for "there is nothing to attach" — which is a sentence the interface should never need to say, because the button that opens it could simply not be there. Abram's word was "nonsensical." When a control's only possible outcome is an apology, remove the control.
- **A marker only protects what it actually names (9/22).** The 9/22 pre-flight reported `importWorklistRequest` missing and it read exactly like a dropped feature. It was a false alarm: CLIENT WORKLIST SUBMISSION was completely intact, and `importWorklistRequest` was a name the SPEC proposed that the build never used — what shipped is `confirmWorklistImport`. A stale marker costs a diagnostic detour every pre-flight until someone fixes it, so when a spec proposes a name and the build lands on a different one, **the shipping chat owns correcting the spec**, not just the hub.
- **Two chats can hold two halves of one instruction (9/22–23).** "Leave the client doc alone" was said in one chat on 9/22; "photos … in the client doc too" was said in another on 9/22. Neither was wrong, and neither chat could see the other. The EDIT_LOCK's last-completed-edit note and this hub's Current state are the only shared memory between them — read both before acting on an instruction about an area, and when the two disagree, **put the conflict in front of Abram rather than picking**. He resolved it in one line on 9/23.
- **A rule I imposed is not a requirement he gave (9/22).** The day view was made read-only in 17c on my own judgment — "two surfaces can never disagree" — and then Abram said he would use it for invoice editing, which the rule forbade. The safety it bought was imaginary: both views were always writing the same entries through the same save path. When you add a constraint nobody asked for, say so out loud at the time, because it will quietly shape what he can do with the thing later.
- **Test the attribute, not the glyph (9/22b).** Two of the first headless run's 22 assertions failed on harness bugs, not engine bugs: the BILLED DAYS header's `textContent` begins with the `▶` chevron, so `startsWith('Billed days')` never matched, and failed image fetches for deliberately-unreachable seed URLs were being counted as page errors. Both were fixed by giving the header a `data-tpm-billed-days` hook and scoping the error filter. **When a check fails, establish whether the code or the check is wrong before touching the code** — and say which it was.
- **`coalesce` guards absence, not correctness (9/22).** The thumb-blob action was "fixed" in August with `coalesce(thumbB64, fullB64)`, which only substitutes when the key is MISSING. On 9/21 the Shortcut started sending `thumbB64: "IMG_1090"` — present, and garbage — and it sailed straight into `base64ToBinary`, killing every run for a day. Any external payload field feeding a decoder needs a SHAPE test (length, prefix), not a null test.
- **A binding can break with nobody touching it (9/22).** The flow was byte-identical to the day it worked; the Shortcut's variable binding had drifted on its own. When a pipeline that "worked for weeks" fails cold, read the RAW TRIGGER PAYLOAD before touching any logic — one look at `"thumbB64": "IMG_1090"` ended the diagnosis. Corollary: bind to NAMED variables, because a name cannot be silently re-pointed.
- **Fail-fast duration is itself a diagnostic (9/22).** 120–380 ms means the run died at template evaluation — not network, not upload, not a big file. And a *template* error names the function that threw. Read the duration column before opening anything.
- **Name an action by its parameters, not its label (9/22).** `Create block blob (V2)` and `Create block blob (V2) 1` differ by one trailing digit whose meaning is the opposite of what it looks like (the "1" is the THUMBNAIL). The first 9/22 fix went into the wrong one and reproduced the identical error. Check Code view's `name` line — `-thumb.jpg` vs `.jpg` — before editing either.
- **Filter before you fetch (9/22).** `fetchPendingPhotos` applies its vessel test to the RESULTS of fetching every marker rather than to the list of marker names, which is invisible at 5 markers and quietly linear-in-the-whole-fleet at 281. A filter that runs after the expensive step is not a filter; it is a receipt.
- **Move the ref, don't copy it (9/22b).** Entry photos could easily have been a second array pointing at the same photos, which would have drawn every attached photo twice — once under its entry, once in the project gallery — and left two places to edit a caption. `attachPhotoToEntry` instead LIFTS the ref out of whatever project, tray slot or other entry held it, so a photo lives in exactly one place by construction, and both galleries additionally subtract `entryHeldPhotoIds()` as belt-and-braces for older data. When one record can belong to two containers, decide which one OWNS it before writing the render.
- **Wrap the old view, don't re-run its builders (9/17, 17d).** The client doc has five card builders and a long history of a "doc-wide change" missing one. The day view avoided that by regrouping the ENTRIES and leaving the project-shaped body untouched inside a wrapper div — which made the proof trivial: export the same seed from the old build and the new one and diff the two documents. When adding a second presentation of the same data, reach for a wrapper and a regroup before reaching for the existing builders.
- **A second view of the same data is a bug detector (9/17).** The day view was built as a convenience and found two things the project cards had been hiding for weeks: unposted hours inflating a project's travel share, and day totals quietly including work Abram had decided not to bill. If a number is hard to check, build the second view before building more features on top of it.
- **"Rejected" can be about input, not output (9/17).** The day-shaped ENTRY form was rejected flat on 9/17 — and hours later Abram asked for a day-shaped VIEW in both the engine and the client doc. The hub entry originally read "do not propose day grouping again", which would have talked a future chat out of exactly what he wanted. When recording a rejection, record what was rejected and why, narrowly enough that the neighboring idea survives.
- **A derived row needs to inherit STATE, not just value (9/17).** `syncTravelDays` faithfully recomputed each travel row's hours and description but left `graduated` at its creation default, so the engine billed labor and quietly pushed its travel to the next invoice. Deriving a figure is only half the job — anything generated from another record must also track that record's workflow state (posted, graduated, which invoice), or it drifts out of step in a way the totals hide.
- **Nothing was stored, so history was never safe (9/17).** Billed amounts were recomputed from the live `RATES` constant on every render, which means the first rate change would have silently re-priced every invoice already sent. A figure you can still recompute is a figure that can still change: freeze what you invoiced at the moment you invoice it, and latch it (`enforceSeals`) rather than trusting every future code path to remember the rule. **The same logic extended to photos on 9/22b — if it is part of what the client was shown with the invoice, it belongs inside the seal.**
- **Hand-typed proration math rots (8/25).** Travel rows whose "0.75 of 4.5 hrs" lived only in the description went stale the moment labor was consolidated or moved. Anything computed from other rows must be DERIVED on save, never authored.
- **Where a control lives is part of whether it works (9/17).** The travel-day card was correct and still felt cumbersome because it sat in the tab Abram treats as a filing cabinet. Before building an input, ask which screen he is actually on when he has the number in hand. **(Corollary, 9/22b: the entry-photo 📷 went into the day view for exactly this reason — that is where he is when he knows which photo belongs to which line.)**
- **Two chats can both claim the same snapshot number (8/27, repeated 9/1).** Read the hub's `_Last updated_` line at write time and take the next free number; if your write is superseded, re-merge rather than assume it landed. **(Confirmed again 9/23: a hub read from earlier in the session was already stale — snapshot #023 had landed under it mid-build.)**
- **"Billed" is a property of the work, not of the lock (9/1).** Flipping status only inside `lockFlock` meant anything locked earlier never moved. Rules about state belong where the state is read (render), not only where it changes. **The same rule, applied to a DATE, is what 22b's BILLED DAYS section tests.**
- **"Clear" wasn't clearing (9/1).** The nav Clear reset projects and entries but not billing events or travel days, so a new vessel would have started with Salish See's locked invoices attached. Any "start fresh" path must enumerate every vessel-scoped store.
- **An unposted entry is a decision, not a backlog (9/1).** 10 of Salish See's 21 complete projects carried unposted entries; I first read them as forgotten work. Abram: they are hours he chose NOT to bill. Ask what a state MEANS to Abram before building a rule on it.
- **A locked event's $ and the QB invoice were different numbers (9/1).** The engine froze work subtotals ($19,890.00) while QB billed the grand total ($22,164.13). Anything labeled as an invoice must carry the number the client actually paid.
- **Roll-forward needs a status test (9/1).** Blanket roll-forward (27g) would have quietly carried a Complete project's unbilled entry to the next invoice. Complete + ungraduated = contradiction → hard stop; in-progress/holding + ungraduated = future work → roll.
- **The client doc has FIVE card builders, not one (9/1, 01b → 01c).** `projBlock` (Auth Needed + In Progress), the COMPLETE loop, the HOLDING PATTERN `futureP` loop, and the four row builders in `exportClientPDF` — plus Billing Event/Billed cards that are invoice tallies. A header-level change must be walked through all of them. Grep for `projDisplayTotal(` and `fd(` in header positions before declaring a doc-wide change done. **(Re-confirmed 9/24: it is also why `proj.notes` has four render sites in the doc and none of them is an "Estimate" section.)**
- **"Estimate" was doing two jobs (9/1).** The scope-line subtotal of a quoted job and the posted cost of a worked job both surfaced as one unlabeled green figure. When a number's meaning depends on context the reader can't see, label the number. **(9/24 is the same lesson one level down: on a T&M project the word "Estimate" was sitting above notes that describe a work plan, not a quote.)**
- **A background script cannot log in to GitHub (9/1).** LaunchAgent git has no TTY and no keychain entry; `git push` fails with `could not read Username … Device not configured` even though GitHub Desktop pushes fine. Either seed the keychain once from Terminal with a PAT, or leave the push to Desktop.
- **WebFetch caches for 15 minutes (9/1).** Checking a just-pushed page returned the stale copy; append a `?v=` query to get a fresh read.
- **A billing event is not the Billing Event (8/27, Salish See).** The pink section tallies graduated entries across EVERY unlocked billing event; Lock freezes one. An event unlocked and never re-locked (504) quietly kept 13 entries and $8,656.75 out of the event Abram was about to lock. Symptom: the pink box doesn't drop to zero after a lock. Fixed by the 27h span guard.
- **A build relayed from another project can arrive without a hub write-up (8/27, 27g).** Protocol rule 7 now assigns that duty to the relaying chat.
- **The hub described an automation that didn't exist (8/27).** The "vessel JSON router" was documented as installed but was never on the Mac. When documenting a Mac-side install, record the verification command and the date it was last seen running — not just the design.
- **A folder-watcher with no age window will eat whatever is already in the folder (8/27).** The v1 router's first run filed three March Moondance exports over `moondance/current.json`. Every watcher now has a 10-minute freshness window AND a newer-than check on the target.
- **Terminal needs its own Full Disk Access entry** — permission is charged to the app that launched the command (Terminal), not to `/bin/bash`, and only takes effect after Cmd+Q/reopen. "Operation not permitted" on a OneDrive path = this.
- **Folder access for Claude is scoped and per-session (8/27).** A chat only ever sees the folder Abram adds in the desktop app; it expires with the session. Grant the narrowest folder that does the job — `Hub Archive`, never a parent.
- **Safari's "allow downloads on ''" prompt** is per-site permission for a page opened from a local file (no domain → empty quotes). Cancel = silent no-save. Fixed via Websites → Downloads → other websites = Allow.
- **Safari download location decides what the automations see.** Moving it (8/27: to OneDrive DOWNLOADS) silently orphans any watcher pointed at `~/Downloads`.
- **Immediate `URL.revokeObjectURL` after `a.click()` kills Safari downloads** — Safari resolves every download asynchronously. Symptom in ⌥⌘L: entries named "Unknown" or "Zero KB — stopped", nothing in the download folder. Always append the anchor and revoke on a timer (fixed 8/27, build 27e).
- Engine build downloads have had many names — that's WHY the auto-lander detects by content marker, never filename. Don't reintroduce filename matching.
- Vessel folders use hyphens but export filenames use underscores — that's why the router reads `_meta.vessel` from inside the JSON.
- The Save-As dialog on export was Safari's download setting, not engine code.
- Writes into `~/Library/CloudStorage/…` are blocked for scripts without Full Disk Access.
- In-place patches to `acurrentengine/index.html` are overwritten by the next build that auto-lands — every UI change must ALSO go into the build source. **Confirmed by example:** the 8/14 v8 upload in this project had LOST the collapsed-tray patch from 8/13.
- **An uploaded engine file can be a stale lineage.** The 8/19 session's base upload predated 2026-08-18a and silently dropped three shipped fixes; the giveaway was stepper arrows visible in screenshots. Compare any upload against the project doc `index.html` before building on it.
- **Parallel chats can fork BOTH the engine doc and this hub.** On 8/20, while one chat shipped 20f, another shipped 20g–i from a pre-20f base — the engine lost the picker and two Billing Event visuals, and the hub was overwritten from an older read. For the hub, always MERGE into the freshest copy (re-read it immediately before writing), never rewrite from a version read earlier in your session.
- **The project doc can change mid-session.** Re-pull the doc AFTER claiming EDIT_LOCK and diff-check the build stamp before editing — a read from even minutes ago may be stale.
- Client docs are GENERATED files — re-export to apply new engine behavior.
- The tray's "temporary remove" is DESIGNED to return photos on Refresh; only "permanent" adds to dismissedPhotoKeys.
- Bare `/<vessel>` URLs on the client site 404 or serve stale engine copies.
- **"Photos don't load" was three separate things at once**: the tray was collapsed and the caret invisible; upstream thumbnails are full-size so opening it fired ~150 MB; Refresh reported nothing either way. Check the affordance FIRST before diagnosing the network.
- **Diagnose a stalled tray by SIZE, not by status code.** 200s with real bytes means storage and permissions are fine and the problem is volume. Compare `-thumb.jpg` byte size against the full image.
- **Shortcuts names every Encode output "Base64 Encoded"** with no way to disambiguate in the picker. Always add a `Set Variable` with a real name right after each encode. **(Re-confirmed the hard way 9/22 — this bullet existed and the named-variable cure was still never applied, so the binding drifted a second time and took the whole pipeline down for a day. A gotcha written down is not a gotcha fixed.)**
- Debug snippets go in the **browser JavaScript console** (Safari: Develop → Show JavaScript Console, ⌥⌘C), not Terminal. zsh chokes on `!` in JS via history expansion, and a pasted multi-line IIFE can silently lose its trailing `()`.
- Photos are scoped per vessel — a test capture tagged `hannah-mae` will never appear in the Sandi Louise tray.
- **A one-shot height measure on hidden content lies.** Anything sized from `scrollHeight` at build time will be wrong whenever the element is inside a collapsed card or measured before layout settles. Re-fit on width change (ResizeObserver).
- **Safari's number-input steppers are always visible** (unlike Chrome's hover-only) and eat ~16px of the cell — any tight numeric column must hide them or budget for them.
- **A client-facing hint must survive the printer and the second visit (9/23).** The NEW-VIEW CALLOUT is `tpe-noprint` (a bill should never carry an onboarding box), starts hidden until its localStorage check so a returning reader sees no flash, doesn't animate (a pulsing box in an invoice reads as an advert), and is dismissed by using the switch as well as by the ×. Anything added to the client doc gets asked these four questions.

- `VESSEL <name>:` per-vessel data or client-doc work
- `ADMIN:` everything else
Rename old chats as you touch them. When a chat produces a decision worth keeping, add one line to this hub.
